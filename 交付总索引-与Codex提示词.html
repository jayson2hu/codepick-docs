CodePick — 4 个产品并行交付 + 统一

四层各自是一个独立产品，每个有 4 份文档（产品 / 架构 / 详尽开发Plan / 实施手册）。本索引把文件夹归属、并行顺序、每个产品的 Codex 提示词、统一接缝与集成步骤全部标注清楚。每个产品可对下层 stub 独立开发，最后按冻结契约统一。

▦总览：4 产品 × 4 文档 = 16 份

产品文件夹独立开发依赖文档数
L0 数据底座L0-数据底座/无（最底层，真实采集）4 ✓
L1 数据加工L1-数据加工/L0 stub + FakeLLM4 ✓
L2 判断与智能体L2-判断与智能体/L1 stub + FakeLLM4 ✓
L3 应用与分发L3-应用与分发/L2 stub + 支付沙箱4 ✓
核心机制：每个产品取下层数据只经一个 Provider 接口（注入 stub 即可独立开发）；产出遵守冻结契约（下层一旦定死，上层照常开发）。这让 4 个产品能真正并行，最后无缝统一。

②并行顺序与依赖

4 个产品可同时开工（各用 stub），但"集成验证"按依赖自下而上。

L0 真实采集 → L1 对 L0 stub → L2 对 L1 stub → L3 对 L2 stub
  • 开发期：4 条线并行，互不阻塞（stub 解耦）。
  • 集成期：自下而上替换 stub —— L1 接真 L0 → L2 接真 L1 → L3 接真 L2。每替换一层跑该层 smoke + 联调。
  • 建议优先级：先确保 L0 真实可用（它无法 stub 自己），其余三层 stub 开发可与之并行。

③Codex 提示词 ×4（复制即用）

每段提示词与对应产品的 4 份文档一起交给 Codex。L2/L3 的提示词也已内嵌在各自《实施手册》末尾，这里集中汇总。

L0 数据底座 · 提示词

# 角色 你是资深 Python 数据工程师，独立实现 CodePick 平台的 L0「数据底座」（采集+完整保存+规范化+去重+事件）。 # 输入材料（同目录 4 份 HTML，先读完） L0-数据底座-产品文档 / 架构设计 / 开发Plan-详尽版 / 实施手册-交付包 # 任务 按《开发Plan》EPIC E0→E8、Feature 顺序实现，逐个用其「验收」+「自测」收口；按《实施手册》脚手架、DDL、接口契约、docker-compose 落地。 # 硬约束 1. 信条：尽可能保存所有信息，原始层不可变、只追加、永不删除；RawStore 仓储不得有 update/delete。 2. 三段存储：原始层(raw_documents+对象存储) / 规范层(content_items) / 索引层；强血缘可溯源。 3. 可重放：能从原始层重建规范层，无需重抓外部源。 4. 去重保留变体：去重只选代表，原始抓取各自留痕。 5. 事件用事务性 outbox，content.ingested 不丢不重。 6. 对上层只暴露稳定查询契约(list_contents/get_content) 与事件；core_data 不得 import 上层。 7. 栈：Python3.12 / Playwright / feedparser / PostgreSQL+pgvector / SQLAlchemy+Alembic / Redis+Arq / S3兼容。 # 交付标准（DoD） 每 Feature 过自测；`make smoke` 输出 "L0 PIPELINE: PASS"；覆盖率≥80%，CI 全绿；满足《实施手册》L0 DoD。产出：可运行代码+测试+迁移+docker-compose+README。 # 工作方式 每 Sprint 提交一次（附已实现 Feature/自测/覆盖率/遗留）。契约歧义先提问，不擅改冻结契约。

L1 数据加工 · 提示词

# 角色 你是资深 Python/LangGraph 工程师，独立实现 CodePick 平台的 L1「数据加工」（清洗+初评+基础分析+向量）。 # 输入材料（同目录 4 份 HTML，先读完） L1-数据加工-产品文档 / 架构设计 / 开发Plan-详尽版 / 实施手册-交付包 # 任务 按《开发Plan》EPIC E0→E9、Feature 顺序实现，逐个用「验收」+「自测」收口；按《实施手册》脚手架、接口契约、LangGraph 图规格、配置落地。 # 硬约束 1. 独立开发：取内容只经 ContentProvider，注入 StubContentProvider + fixtures；LLM 用 FakeLLM。不依赖真 L0、不真调模型。 2. 与垂直无关：L1 只做通用理解（摘要/观点/金句/实体/向量/基础标签），绝不含"对某垂直好不好"的判断。 3. 冻结契约：BaseAnalysis schema + 事件 content.analyzed + 表归属（只写 content_base_analysis/enrichment_cache，只读 content_items）。 4. 成本：小模型初评短路 + 缓存 + 并发限流；模型档位走 ConfigKey。 5. 所有 LLM 节点可用 FakeLLM 确定性测试，CI 不真调模型。 6. 栈：Python3.12 / LangGraph / PostgreSQL+pgvector / SQLAlchemy+Alembic / Arq。 # 交付标准（DoD） 每 Feature 过自测；`make l1-smoke` 输出 "L1 PIPELINE: PASS"；覆盖率≥80%，CI 全绿；满足《实施手册》L1 DoD。产出：代码+测试+迁移+README。 # 工作方式 每 Sprint 提交一次。契约歧义先提问，不擅改冻结契约。

④冻结契约（统一接缝 — 必须对齐）

这是 4 个产品最后能拼起来的关键。各产品的 Codex 都被要求不得擅改这些契约。

L0 → L1  事件 content.ingested {content_id,lang} · 查询 get_content/list_contents
          表归属: L0 拥有 sources/raw_documents/content_items/content_versions
L1 → L2  事件 content.analyzed {content_id} · 产物 BaseAnalysis(schema)
          表归属: L1 拥有 content_base_analysis/enrichment_cache（只读 content_items）
L2 → L3  事件 content.completed {content_id} · 产物 VerticalScore + content_translations
          请求时 recommend()/companion() · 表归属: L2 拥有 verticals/vertical_scores/translations/review_queue
L3      拥有 users/subscriptions/interests/follows/reading_events/briefs/bookmarks/api_keys/usage（只读 L0–L2）
状态机（全局共享）: WAIT_FILTER→WAIT_ANALYSIS→WAIT_SCORE→WAIT_REVIEW→COMPLETED | CANCELLED
表归属互不重叠→集成时迁移自然合并，无冲突；事件主题统一→接同一总线即通；Provider 接口→把 stub 换真实现即对接。

⑤统一集成步骤

4 个产品各自交付（代码+测试通过各自 DoD）后，按此统一。

  • 1. 合库：4 个工程并入一个 monorepo（或保持多仓 + 共享 common + 统一迁移目录）。
  • 2. 合并迁移：各层 Alembic 迁移按归属合并；因表互不重叠，无冲突。
  • 3. 接事件总线：把各层的 outbox/consume 接到同一 Redis/事件总线（content.ingested→analyzed→completed 串起）。
  • 4. 替换 Provider：L1 的 ContentProvider→真 L0；L2 的 AnalysisProvider→真 L1；L3 的 ContentReadProvider→真 L2。
  • 5. 逐层联调：自下而上每接一层跑该层 smoke + 全链 smoke。
  • 6. 全链冒烟：一条真实内容从采集→加工→评分→在 Reader 展示，端到端 PASS。
  • 7. 接真实外部：真实 LLM、真实支付（沙箱→生产）、真实邮件。
因为契约从第一天就冻结，统一集成主要是"换注入 + 合迁移 + 接总线"，不是重写。这正是分层 + stub 并行开发的回报。

⑥怎么用（操作清单）

  • ① 新建 4 个文件夹（见 §1），各拖入对应 4 份 html。
  • ② 想先做哪个就开哪个 Codex 会话：把该文件夹的 4 份 html + §3 对应提示词一起给它。
  • ③ 4 个产品可并行（各用 stub）；优先保证 L0 真实可用。
  • ④ 每个产品按其《开发Plan》逐 Feature 实现 + 自测，Sprint 末跑该层 smoke。
  • ⑤ 各自通过 DoD 验收后，按 §5 统一集成。
  • ⑥ 全程不改 §4 冻结契约——这是能拼起来的保证。
