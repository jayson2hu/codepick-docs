产品二：Agent-first 策展 API / MCP

把"高质量内容 + 结构化判断"开放为人和智能体都能调用的稳定原语。它不重建采集与分析，而是复用与产品一同一个内容中台和垂直判断层，只新增"受控对外暴露"——API Key 鉴权、限流配额、版本治理，以及一层 MCP Server。

定位与边界

🎯

它负责

稳定原语 REST API、API Key 鉴权、限流/配额、版本治理、MCP Server、开发者门户/文档

🔗

它复用

共享中台（采集/实体/基础分析）+ 垂直判断层（VerticalScore）——与产品一同一份数据

🚫

它不暴露

内部推荐决策、用户隐私上下文、后台审核流程、内部任务状态

为什么几乎零额外成本：产品一已经把内容采集、基础分析、垂直评分都做好并写进共享库了。产品二只是在这份已有的结构化数据上加一层"受控读接口 + MCP 封装"。这正是上一轮"共享数据核心"结论的直接收益——同一份判断，两种消费方式（人用 Web，Agent 用 API）。

② 复用共享中台（复用边界）

复用·只读
内容实体 + 基础分析
直接查询 content_items / content_base_analysis，不重新抓取、不重新分析。
复用·只读
垂直判断层 VerticalScore
查询 content_vertical_scores（COMPLETED）。"今日精选/搜索/深度分析"都基于这层。
本产品新增
受控暴露层
API Key、限流、配额、字段裁剪（隐藏内部字段）、稳定契约与版本。
本产品新增
MCP 适配层
把 REST 原语包装成 MCP tools，供智能体直接调用。
关键纪律：对外只暴露稳定原语，不透出内部实现。读取走独立的对外查询服务（或同库不同视图），与产品一的 BFF 在信任边界上分离——不同前缀、不同过滤器、不同鉴权。

④ 核心模块 (C4 Level 3)

模块职责关键点
API Gateway / 过滤器链统一入口：鉴权→限流→配额→裁剪顺序固定；任一不过直接拒；与产品一前缀/信任边界分离
API Key 服务签发/吊销/scope 管理存 hash；Redis 优先读，miss 回源 PG 回填
限流 + 配额速率限制 + 每日用量Redis 共享计数（跨节点）；超限返回 429 + 重置时间
原语服务today/search/item/trending/sources只读 COMPLETED；统一分页与排序；字段裁剪
MCP Server把原语包装成 MCP toolsnpm 分发；支持 stdio + 远程 HTTP；工具描述对 LLM 友好
开发者门户Key 自助生成、用量看板、OpenAPI 文档可挂在产品一 /settings 或独立站

⑤ 稳定原语 (REST API)

Base：https://api.yourdomain.dev/v1 · 鉴权：Header X-API-KEY · 全部只读、幂等。

GET/v1/today某垂直今日最值得读 Top Nvertical, limit, minScore, lang

⑥ MCP 工具设计

MCP Server 是 REST 原语的薄封装，工具命名与描述对 LLM 友好（动词清晰、参数少、返回结构化）。

MCP Tool映射端点典型用法（自然语言触发）
bestpick_todayGET /v1/today"今天 AI Coding 有什么值得读的？"
bestpick_searchGET /v1/search"找几篇关于 RAG 评测的高分文章"
bestpick_analyzeGET /v1/items/:id"把这篇的结构化分析给我"
bestpick_trendingGET /v1/trending"本周这个领域在热议什么"
bestpick_sourcesGET /v1/sources"这个垂直有哪些优质源"

分发与安装

# 用户安装（npm）
npx @yourbrand/mcp            # 启动 MCP server

# Claude / Cursor 配置 mcp.json
{ "mcpServers": {
    "bestpick": {
      "command": "npx", "args": ["@yourbrand/mcp"],
      "env": { "API_KEY": "sk_..." }
    } } }
差异化卖点："任何 Agent 一行调用，拿到某领域今日最值得读的内容 + 结构化分析"。这是产品一前端站给不了的场景，也是当前 MCP 生态稀缺的"高质量内容上下文"供给。

⑦ 数据模型

复用（与产品一同库，只读）

content_items · content_base_analysis · content_vertical_scores · verticals
-- 不重建，直接查询 COMPLETED 内容。字段经"裁剪层"对外，隐藏内部字段。

本产品独有（鉴权与计量）

table api_keys
  id, owner_user_id, key_hash unique, prefix, scopes text[],
  rate_limit_rpm int, daily_quota int, status[active|revoked], created_at

table api_usage_daily          -- 配额计数（Redis 原子计数 + 落库）
  key_id, day, count, primary key(key_id, day)

table api_request_log          -- 审计/分析（可采样）
  id, key_id, endpoint, status, latency_ms, ts
实现演进（与 BestBlogs 一致）：限流/配额计数当前态可用进程内 + DB 原子计数起步；目标态迁到 Redis 共享计数以支持多节点。API 契约保持不变，仅换底层实现。

⑧ 关键流程时序

A. REST 请求（带鉴权/限流/配额）

客户端带 X-API-KEY 请求 /v1/today
API Key 校验：Redis 查 key 元数据（miss 回源 PG 回填）；无效 → 401
限流：Redis 滑窗计数，超 rpm → 429（带 Retry-After）
配额：原子自增当日计数，超 daily_quota → 429（带 resetAt）
原语服务查询 COMPLETED 垂直评分 + 基础分析，裁剪字段后返回
异步写 api_request_log（可采样）

B. MCP 工具调用

Agent（Claude/Cursor）触发 bestpick_today({vertical})
MCP Server 用环境里的 API_KEY 调内部 /v1/today
把结构化 JSON 作为工具结果返回给 LLM；LLM 据此回答用户

⑨ 鉴权 / 限流 / 配额 / 版本治理

鉴权与信任边界

  • 对外仅 /v1/* + API Key；与产品一 /api/*（内部 Token/JWT）边界隔离
  • Key 存 hash、带 scope；可吊销；前缀便于识别
  • OAuth/Webhook 等回调入口走各自签名校验，不混入

版本与契约

  • 路径版本 /v1、/v2 并行；破坏性变更走灰度
  • v1 下线须等接入方完成切换通知
  • 响应含 quota 元信息，便于客户端自治
分层免费开发者商用
速率 (rpm)20120自定义
每日配额2005,000按量计费
scopetoday/search+analyze/trending全部 + SLA

具体数值交运营 ConfigKey 维护，此处仅示意分层结构。

⑫ 开发里程碑

N1 · 前置依赖

产品一中台 + 垂直评分已产出 COMPLETED

产品二建立在已有结构化数据上，故先有产品一 M1-M2。

N2 · 原语 + 鉴权

REST /v1 + API Key + 限流配额

today/search/item 先行；Redis 计数；字段裁剪层。

N3 · MCP 封装

MCP Server + npm 包

5 个工具；stdio 起步；Claude/Cursor 跑通。

N4 · 门户 + 文档

开发者门户 + OpenAPI

自助 Key、用量看板、可复制片段。

N5 · 分发 + 变现

生态投放 + 计费分层

MCP 市场/社区；免费→开发者→商用分层；按量计费。

排序原则：产品二是产品一的"顺手延伸"，不应抢在 Reader 验证 PMF 之前重投入。建议 Reader 跑到 M4（留存验证）后，用 N2-N3 低成本卡位 Agent 生态作为差异化标签。
