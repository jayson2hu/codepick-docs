# L1 → L2 SQL 快照契约 v1

制定与实测：2026-09-12（M1）。本契约描述已经实现的本地数据边界，不代表生产消息与历史版本消费已经完成。

## 表和数据所有权

L1 写入 `content_base_analysis`；L2 的 `SqlAlchemyAnalysisProvider` 仅反射和读取该表，无需 L0 的 `content_items`，不导入 L0/L1 的 Python 实现。可将各层数据库分开部署；L0 正文和来源在 L1 分析时形成输入快照。

L1 拥有 `content_base_analysis`、`enrichment_cache`、`l1_processing_runs`、`l1_outbox_events`、`l1_schema_migrations`。L2 新增 `content_judgment_state`、`judgment_outbox`，保留原有 `verticals`、`content_vertical_scores`、`content_translations`、`review_queue`。各层迁移只修改本层表。

## 必需快照列

| 列 | 类型/含义 |
| --- | --- |
| schema_version | 整数 1；未知版本明确拒绝 |
| content_id | L1 内部字符串；跨 L2 必须是标准正整数字符串，范围 1..2^63-1 |
| input_snapshot | JSON 原始输入快照：content_id、title、body、source_url、author、published_at、metadata |
| analysis | 成功的 BaseAnalysis JSON；包含 content_id、summary、key_points、entities、base_tags、embedding、lang、status 等 |
| graph_version | 非空版本字符串 |
| content_hash | 清洗后标题/正文的 hash，用于内容缓存 |
| run_id | 非空的本次处理标识 |
| status | L1 处理状态；仅 WAIT_SCORE 可被 L2 读取 |
| updated_at | 最后提交时间 |

L1 还保存 `request_id` 与并发控制 `revision`，L2 当前无需使用这些内部列。FAILED/CANCELLED 行的 analysis 可空，L2 不允许将它们当成可评分结果。

## 映射到 L2 BaseAnalysis

| L2 字段 | L1 来源 | 校验/回退规则 |
| --- | --- | --- |
| content_id | 请求 ID、表 content_id、input_snapshot.content_id、analysis.content_id | 必须全部一致；拒绝 bool、浮点、前导零、不透明字符串和超 BIGINT 范围值 |
| title | input_snapshot.title | 必须为字符串，可空；保持 L0 允许缺标题的语义 |
| text | input_snapshot.body | 必须为非空正文；不从引用路径猜测正文，不回退 fixture |
| source | input_snapshot.metadata.source.name | 空缺时使用 source_url；两者均无值时报错 |
| language | analysis.lang | 空缺时使用 metadata.lang；仍为空时报错 |
| summary | analysis.summary | 非空字符串 |
| key_points | analysis.key_points | 非空字符串列表 |
| entities | analysis.entities | 字符串列表，可为空 |
| tags | analysis.base_tags | 非空字符串列表 |
| embedding | analysis.embedding | 非空有限数值列表；拒绝 bool、NaN、Infinity；不能偷偷用空向量 |
| exposure | metadata.exposure | 未提供为 0；只接受非负整数 |

快照外层 status 必须为 WAIT_SCORE，analysis.status 必须为 COMPLETED。L2 不把必需字段缺失转换成空值或 unknown 以掩盖契约错误。旧手工构造双表的兼容 adapter 仍保留，但不用于 M1 实际链路。

## 版本、处理请求和通知

L1 默认以内容输入快照与 graph_version 定义自动处理请求。成功的当前输入重复调用返回已保存结果；正文/来源等快照变化、graph_version 变化会建立新结果和新通知。输入或 graph 回退到历史值时必须更新当前投影，不能返回旧历史成功却仍让 SQL 读取另一版本。

`reprocess_key` 明确要求跳过缓存重新计算。同一内容的同一个 key 重试保持幂等；将同一 key 用于另一输入或 graph_version 会报冲突。模型/校验失败保留处理记录并允许再次尝试；缓存命中不增加模型调用量。数据库提交失败不会留下成功记录或半份通知。

每个成功 run 的通知主题仍为 `content.analyzed`，事件 ID 为 `content.analyzed:{run_id}`；payload 包含 schema_version、content_id、run_id、graph_version、content_hash、status 和 analysis。分析当前投影、处理记录/成本、缓存和 outbox 在同一数据库事务内提交。并发提交使用 revision 条件校验，过时结果必须重新读取后重试。

`relay_once` 提供至少一次投递；回调异常时不标记发送成功，回调成功才确认。若接收成功后进程在确认前退出，允许使用相同 event_id 重投，接收方必须据此去重。该语义不是无条件“恰好一次”。

## 尚未闭环的版本边界

- L0 当前稳定查询不直接暴露 current_version/content_hash；L1 自己对输入快照与正文计算 hash。
- L0 同 URL 正文更新尚无新版 content.ingested 自动通知；M1 测试更新后显式再次调用 L1。
- L2 当前读取“最新可评分快照”，未按事件 run_id 读取历史版本。COMPLETED/CANCELLED/WAIT_REVIEW 的重复任务保留持久终态，不重新调用模型；这不等同于支持新版重评分。
- L2 当前 completion outbox 每内容保留一个完成通知，还没有消息投递确认字段或版本生命周期。
- 下一阶段必须让事件版本、查询快照和 L2 重评分策略共同一致，不能单独放开终态迁移。
