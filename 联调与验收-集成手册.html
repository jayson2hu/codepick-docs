CodePick — 联调与验收集成手册

4 个项目（L0/L1/L2/L3）各自独立开发完成、过了自己的 DoD 后，本手册指导你把它们分别启动、互相联调、最终验收。核心方法：共享一套基础设施，自下而上把每层的 stub 换成真实下层，逐阶段验证，最后跑通端到端真实内容。

i定位与前提

前提：4 个项目各自已通过自己的冒烟与 DoD（make *-smoke = PASS）。本手册不处理单层内部 bug，只处理"拼起来"。

能拼起来的根据：4 层在开发期就遵守了冻结契约——事件主题统一、产物 schema 固定、数据库表归属互不重叠、跨层只经 Provider 接口。联调本质 = 换注入 + 共享基础设施 + 接事件总线，不是重写。

1联调架构（共享基础设施）

                     一套共享基础设施（联调期所有项目都连它）
        ┌───────────────── PostgreSQL + pgvector ─────────────────┐
        │  L0 表  │  L1 表  │  L2 表  │  L3 表   （归属互不重叠）   │
        └──────────────────────────┬──────────────────────────────┘
        ┌──────────── Redis（事件总线 + 队列 + 缓存 + 限流）─────────┐
        │  topics: content.ingested → analyzed → completed         │
        └──────────────────────────┴──────────────────────────────┘
                       ┌────────── 对象存储（原文/媒体）──────────┐
   ┌──────────┐  ingested  ┌──────────┐ analyzed ┌──────────┐ completed ┌──────────┐
   │ L0 采集 │──────────▶│ L1 加工 │────────▶│ L2 判断 │─────────▶│ L3 应用 │
   │ worker   │            │ worker   │          │ worker   │           │ web/api  │
   └──────────┘            └──────────┘          └──────────┘           └──────────┘
   真实抓取                 读 content_items      读 base_analysis      读 COMPLETED+scores
   写 raw/content          写 base_analysis      写 vertical_scores    渲染/早报/计费
联调 = 把"假数据"换成"真数据流"。开发期各层从 fixtures 取数；联调期统统连同一个 PG + 同一个 Redis，数据沿 ingested→analyzed→completed 真正流过四层。

2前置：统一基础设施

2.1 起一套共享 infra

# 用任一项目的 deploy/docker-compose（4 份内容一致），只起一次
docker compose -f deploy/docker-compose.yml up -d   # postgres+pgvector / redis / minio

2.2 合并数据库迁移

# 因表归属互不重叠，4 套 Alembic 迁移可合并到一处按序执行
alembic upgrade head     # 顺序: L0 表 → L1 表 → L2 表 → L3 表
# 若 4 仓各自有 alembic head，合并为一条迁移链（multiple heads → merge）
alembic merge -m "integrate L0-L3" <heads> && alembic upgrade head

2.3 统一连接配置（所有项目指向同一 infra）

DATABASE_URL=postgresql+psycopg://codepick:dev@localhost:5432/codepick   # 四项目相同
REDIS_URL=redis://localhost:6379/0                                       # 同一实例/同一 db
S3_ENDPOINT=http://localhost:9000  S3_BUCKET=codepick-raw
# 关键：关闭各层的 stub 开关
L1_USE_STUB=false   L1_USE_FAKE_LLM=false
L2_USE_STUB=false   L2_USE_FAKE_LLM=false
L3_USE_STUB_L2=false
# 接真实外部（联调后期）
LLM_API_KEY=...     PADDLE_*（沙箱→生产）   RESEND_API_KEY=...
最易踩的坑：① Redis 必须是同一实例同一 db，否则事件发出去没人收；② 事件 topic 名四层必须逐字一致（content.ingested/analyzed/completed）；③ 各层的 *_USE_STUB 开关必须确实关掉。

3各项目启动方式（分别启动）

项目启动什么命令（示例）
L0采集 worker + 调度uv run arq workers.ingestion.worker · core-data source import seed.opml
L1enrichment workeruv run arq workers.enrichment.worker
L2scoring worker（+ seed ai-coding lens）uv run arq workers.scoring.worker
L3reader-api + reader-web + briefs worker（+ public-api/mcp 可选）uvicorn reader_api.main:app · pnpm --filter reader-web dev · uv run arq workers.briefs.worker
顺序无所谓，但都连同一 infra。worker 是事件驱动的，先起后起都能消费到队列里的消息。建议：先把 4 个项目都连好配置、各自能起来不报连接错误，再开始推数据联调。

4联调策略：自下而上，逐层接真

不要四层一起接真后才测。每接通一层就验证一层，问题范围最小化。

阶段1  只 L0：真实采集 → 验证 content_items / raw / ingested 事件
阶段2  + L1：ingested 自动触发加工 → 验证 base_analysis / analyzed 事件
阶段3  + L2：analyzed 自动触发评分 → 验证 vertical_scores / translations / completed / COMPLETED
阶段4  + L3：COMPLETED 内容上 Reader、进早报、可被 /v1 调用 → 全链打通

▸阶段1L0 真实自检

动作 启动 L0，导入真实源，跑一轮采集
core-data source import seed.opml      # 真实 AI Coding 源
core-data ingest run --all            # 或等调度自动触发
✓ 验证 
-- 有真实内容入库
SELECT count(*) FROM content_items WHERE status='WAIT_FILTER';   -- > 0
-- 原文完整保存可溯源
SELECT raw_html_ref, raw_html_sha256 FROM raw_documents LIMIT 1; -- 非空
-- 事件已发出
SELECT count(*) FROM outbox_events WHERE topic='content.ingested' AND published_at IS NOT NULL;

▸阶段2L0 + L1 联调

动作 启动 L1 worker（stub 关闭，连共享 infra）

L1 的 ContentProvider 现在读共享 DB 的真实 content_items；消费 Redis 上 L0 发的 content.ingested。

✓ 验证（内容自动从 ingested 流到 analyzed） 
SELECT count(*) FROM content_base_analysis;                      -- 随时间增长
SELECT status, count(*) FROM content_items GROUP BY status;      -- 出现 WAIT_SCORE
SELECT count(*) FROM outbox_events WHERE topic='content.analyzed';
-- 抽查一条：摘要/观点/向量齐全
SELECT one_liner, summary, jsonb_array_length(key_points), (embedding IS NOT NULL)
FROM content_base_analysis LIMIT 1;
若 base_analysis 不增长：检查 ① L1 是否消费到 ingested（Redis 同实例？topic 名？）② L1_USE_STUB=false？③ LLM 凭证有效？看 L1 worker 日志。

▸阶段3+ L2 联调

动作 seed ai-coding lens，启动 L2 worker

L2 的 AnalysisProvider 读真实 content_base_analysis；消费 content.analyzed。

✓ 验证（流到 completed） 
SELECT count(*) FROM content_vertical_scores WHERE vertical_code='ai-coding';
SELECT dim_scores FROM content_vertical_scores LIMIT 1;          -- 六维分合法
SELECT count(*) FROM content_translations;                       -- 中英
SELECT status, count(*) FROM content_items GROUP BY status;      -- 出现 COMPLETED
SELECT count(*) FROM outbox_events WHERE topic='content.completed';
若卡在 WAIT_SCORE：检查 lens 是否 seed、relevance_gate 是否把内容判成"不属于该垂直"、L2 是否消费到 analyzed。

▸阶段4+ L3 全链

动作 启动 reader-api / reader-web / briefs worker（L3 读真实 L2 产物）
✓ 验证（终端可见）
  • 打开 / 公共精选 → 看到刚采集分析的真实文章，含评分/双语摘要
  • 详情页 /read/:id → 摘要/观点/金句/六维分/中英切换正常
  • 触发早报 Job → briefs 出现今天的早报项；邮件发出
  • AI 伴读对该文提问 → 流式返回（reader-api 代理 L2 companion）
  • （可选）GET /v1/today?vertical=ai-coding 带 key → 返回该文
  • Free 账户访问 Pro 功能 → 被门禁拦截；支付沙箱升 Pro → 放行
四阶段全过 = 全链打通。一条真实内容已从"采集"走到"在 Reader 上被读"。

5端到端验收用例（黄金路径）

用例：一条真实文章的完整旅程

  • ① 在 L0 登记一个真实 AI Coding 源，触发采集
  • ② 数分钟内，该源新文章自动：采集 → 加工 → 评分 → 翻译 → COMPLETED（无人工干预）
  • ③ 该文出现在 Reader 公共精选与详情页，含六维分 + 中英分析
  • ④ 该文进入当天公共早报，邮件可收到
  • ⑤ 对该文用 AI 伴读提问，得到基于内容的回答
  • ⑥ /v1/today 与 MCP bestpick_today 能返回该文
  • ⑦ 升级 rubric/graph 版本 → 触发 reprocess → 该文被重新加工评分（验证可重放）

全部通过 = 平台级端到端验收 PASS。

现象定位与解决
下游表不增长（如 base_analysis 一直空）上游事件没被消费：查 Redis 同实例？topic 名？消费者在跑？stub 关了吗？看该层 worker 日志
内容卡在某状态对应层未运行/在报错；查该层 worker 日志与状态机转移逻辑

schema 不匹配/反序列化失败契约漂移：对照冻结契约（BaseAnalysis/VerticalScore）逐字段比对，回退到契约

8最终验收清单（平台级 DoD）

  • 全链自动：真实源新内容自动走完 采集→加工→评分→翻译→COMPLETED，无人工干预
  • 数据完整：原文/分析/评分/翻译可溯源；L0 全量保存可校验
  • 终端可见：COMPLETED 内容在 Reader 公共精选/详情双语正确呈现
  • 个性化：登录后我的早报/推荐基于真实评分生成；行为埋点支撑北极星
  • 分发：公共/我的早报生成并邮件投递
  • 伴读：基于真实内容流式问答；Free/Pro 配额生效
  • 商业化：支付（沙箱）升/降级闭环，门禁正确
  • 开放（可选）：/v1 原语 + MCP 返回真实数据，限流配额生效
  • 可重放：升级 rubric/graph 版本可对历史内容重处理
  • 可观测：四层各有日志/指标；端到端黄金路径用例 PASS
  • 回归：四层各自单测 + 全链冒烟在 CI 全绿
全部勾选 = CodePick 平台联调验收通过，可进入接真实外部（LLM/支付/邮件生产）与上线准备。

9回滚与应急

  • 单层回退：任一层出问题，把它的 Provider 暂时切回 stub，隔离排查，不阻塞其他层联调。
  • 事件重放：丢消息时用 L0 的 reprocess(scope) 重新发事件，驱动下游重算（幂等保证不重复）。
  • 数据安全：原始层不可变，任何重算都从原始层派生，不会损坏真相源。
  • 迁移回滚：alembic downgrade 按层回退；因表归属隔离，互不影响。
